# 構成案：パスワードとパスキー

- テーマ：パスワードとパスキー。名前は似ているけど、全く違う安全性。
- 元ネタ：https://www.youtube.com/watch?v=Ao2tY0J-xyE
- 狙い：名前の近さから入って、「送る秘密」と「送らない証明」の設計差で安全性が分かれることを一本の線で伝える。
- 想定尺：会話本編 35〜45分相当（チャレンジ説明・二段階認証・「まだパスワードが多い理由」を厚くした版）
- トーン：事実と仕組みを先に置く。評価語や煽りから入らない（GUIDELINES準拠）。

---

## 全体の一本線

1. 名前は似ている
2. パスワードは秘密を送る
3. パスキーは秘密を送らない（チャレンジ応答。RSAで話した電子署名と同じ発想）
4. だから攻撃面が違う
5. 生体認証・二段階認証との違いを整理する
6. なのにまだパスワード入力が多い理由（移行の途中／逃げ道が残っている）
7. だから「似て非なる安全性」になる。啓蒙より設計。

聞き手が持ち帰る一文：

> パスワードは秘密を渡す認証。パスキーは秘密を渡さずに本人だけができる操作で証明する認証。

追加の持ち帰り（仕組み理解用）：

> チャレンジは「その場限りのテスト問題」。秘密鍵で答え、公開鍵で採点する。指紋は採点ではなく、手元の鍵を使う許可確認。

- 問い：「パスワード」と「パスキー」。名前は近い。中身も近いのか。
- 現実の接点：証券・Google・Appleなどで「パスキーを設定」と出る画面が増えている。
- 予告：似ているのは名前まで。安全性の仕組みは別物。

**話の種（よーた想定）：**
- 「パスキーって指紋ログインの別名？」
- 「パスワードマネージャがあればもう十分？」

### 1. パスワードが弱い、の手前で止まらない（約4分）

**目的：** 「弱いパスワードが悪い」で終わらせない。設計の話へ進む。

- 使い回し・短い文字列・辞書攻撃は確かに問題。
- ただし本丸はそこではない。
- 本丸：認証のたびに「秘密そのもの」を相手へ渡す設計になっている。

**たとえ（1つに絞る）：**
- 家を買う現金を持ち歩いて渡す／銀行振込で済ます。
- パスワードは前者に近い。

**やってはいけないこと：**
- 「人類は愚か」「パスワードは死んだ」から入る。
- ランキングや恐怖事例の羅列で尺を使う。

### 2. パスワードの攻撃面を地図にする（約5分）

**目的：** 「どこで取られるか」を整理し、後のパスキー対比の土台にする。

攻撃面を4点に絞る。

1. 入力時：覗き見、手元の盗み見
2. 送信先の取り違え：偽サイト（フィッシング）
3. 保管先：サービス側に残る関連情報（ハッシュ等）。運用次第では平文もありうる
4. 人の運用：メモ、使い回し、読み上げ誘導

ここで一度まとめる。

> パスワード方式は、秘密が外に出る前提の認証である。

### 3. パスキーの正体：チャレンジを丁寧に説明する（約10分）

**目的：** 「パスキーって何？チャレンジって何？」を飛ばさず説明する。ここが本編の核。尺を厚くする。

#### 3-1 先に結論の形を置く
- やりたいこと：秘密を渡さずに、「本人だけができること」を見せて通る。
- パスワード方式：秘密そのものを送って照合する。
- パスキー方式：その場のテストにだけ答え、答え合わせに使う材料だけを送る。

#### 3-2 登録（鍵を作る）
1. 「このサイト用のパスキーを作る」と端末が動く
2. 端末の中で秘密鍵と公開鍵のペアができる
3. 公開鍵だけがサービスへ渡る
4. 秘密鍵は端末の外へ出ない

ここで一度止める。

> サービスが知っているのは公開鍵だけ。秘密は最初から送っていない。

#### 3-3 チャレンジとは何か（ゆっくり）

チャレンジを「その場限りのテスト問題」として説明する。

1. ログインしようとする
2. サービスが、使い捨てのランダムなデータ（チャレンジ）を作る
3. サービスは利用者に「この問題に、あなたの秘密鍵で署名して返せ」と求める
4. 端末は秘密鍵を使って署名結果を作る
5. サービスは手元の公開鍵で、その署名が本物か確かめる
6. 正しければ「秘密鍵を持っている本人だ」と判定してログインさせる

何を送っていて、何を送っていないかを明示する。

| 送るもの | 送らないもの |
|----------|--------------|
| チャレンジへの署名結果 | 秘密鍵 |
| （登録時の）公開鍵 | パスワード相当の再利用秘密 |
| | 指紋・顔などの生体データ |

たとえは1つに絞る。

> 毎回ちがうクイズを出して、「このクイズに、あなたしか作れない答え方で答えろ」と言う。答えを見て本人だと分かる。クイズの答え方の秘訣そのものは渡さない。

#### 3-4 RSAで話した仕組みと同じ発想
- 以前の暗号回で扱ったRSA／公開鍵暗号の家系である。
- 通信の暗号化でよく出るのは「公開鍵で暗号化し、秘密鍵で戻す」。
- パスキーで使うのはその逆方向の使い方、電子署名である。「秘密鍵で痕跡を付け、公開鍵で確かめる」。
- アルゴリズム名が毎回RSAとは限らない。いまのパスキー実装では楕円曲線署名が多い。だが聞き手に伝える核は同じでよい。

台本での言い方の例：

> パスキーの本体は、RSAの回で話した公開鍵と秘密鍵の発想です。今回は暗号化そのものではなく、電子署名として使います。

避けたい言い方：

- 「パスキー＝RSAそのもの」（実装の一般化としては不正確）
- 「チャレンジ＝パスワードの代わりの文字列」（秘密の再利用と誤解される）

#### 3-5 対比の決め台詞（短く）
- パスワード：秘密を送る
- パスキー：その場の問題にだけ答え、秘密は送らない

#### 3-6 QRコード（短く）
- パスキーが別端末にあるときの橋渡し。
- パスキーの本質ではない。本質は署名による証明。

### 4. 「全く違う安全性」を攻撃ごとに示す（約5分）

**目的：** 抽象論で終わらせず、同じ攻撃面で比較する。

| 攻撃 | パスワード | パスキー |
|------|------------|----------|
| 偽サイト | 入力すれば秘密が渡る | サイトごとに鍵が違う。中継しても本物の証明に転用しにくい |
| サーバー侵害 | 関連情報が漏洩しうる | 秘密鍵は元々ない |
| 覗き見・メモ | 効く | 入力すべき秘密がない |
| 「画面の記号を読み上げて」 | 効くことがある | 所有者でも鍵の中身を取り出せない |

ここでテーマ文を回収する。

> 名前は似ている。だが片や秘密の運搬、片や秘密を動かさない証明。安全性の前提が違う。

---

### 5. 生体認証・スマホ・二段階認証との整理（約6分）

**目的：** 「指紋やスマホ認証＝二段階認証の延長」という印象をほどき、パスキーとの違いを明確にする。聞き手の疑問に正面から答えるセクション。

#### 5-1 聞き手が持っていそうな印象
- パスワードを入れたあと、スマホに通知が来る／指紋を求められる。
- だから生体認証やスマホ確認は、パスワードを残したままの二段階認証として使われている。

この印象は、多くのサービスでは正しい。

#### 5-2 二段階認証の基本形
- 第1要素：パスワード（知っていること）
- 第2要素：スマホの承認、SMSコード、認証アプリの数字、端末の生体認証など（持っているもの／本人性）
- ここでの生体認証やスマホは、パスワードのあとに足す追加確認である。
- パスワード自体はまだ送っている。秘密を渡す設計は残っている。

#### 5-3 パスキーは何が違うか
- パスキーは、理想形ではパスワードの置き換えである。二段階の「追加」ではない。
- ログインの本体が、チャレンジ応答の公開鍵認証になる。
- 指紋や顔はサーバーへ送る第2要素ではない。端末の中で「この秘密鍵を使ってよいか」を確認する鍵の解錠である。

短い対比：

| | よくある二段階認証 | パスキー |
|--|--------------------|----------|
| パスワード | まだ使う | 使わない（置き換える） |
| スマホ／生体 | 追加の確認として外に効くことが多い | 手元の秘密鍵を使う許可 |
| サーバーが受け取る本体 | パスワード＋コード等 | 署名結果 |
| 役割 | パスワード認証を補強する | パスワード認証をやめる |

#### 5-4 混同しやすい現実
- 移行期のサービスは、パスワード＋パスキー、パスワード＋スマホ承認など、併用が多い。
- 画面上はどれも「指紋してください」に見えやすい。
- 見分け方の問い：いま自分はパスワードも打ったか。打っているなら、それは二段階認証側の体験である可能性が高い。打たずに端末確認だけで通るなら、パスキー側の体験に近い。

#### 5-5 誤解の回収
- 誤解A：パスキー＝生体認証 → 違う。本体は秘密鍵。
- 誤解B：スマホ必須の二段階と同じ → 違う。パスキーはパスワード置換が本筋。
- 誤解C：指紋がサービスに保存される → 違う。端末内の解錠に使う。
- 誤解D：パスワードマネージャと同じ → 違う。マネージャは強い秘密の管理。パスキーは秘密を送らない設計。

### 5.5 それでもパスワード入力が多い理由（約5分）

**目的：** 「仕組みは分かった。でも画面ではまだパスワードばかりでは？」という当然の疑問に答える。技術が弱いからではない、と整理する。

よーた想定の一言：

> でもさ、まだまだパスワードを入力させる機会多くね？なんで？

答えの芯：

> パスキーの方が安全でも、世の中はまだ移行の途中だから。安全な道を用意したあと、古い道をすぐ閉じられない。

理由は4つに絞る。増やしすぎない。

1. **逃げ道としてパスワードを残している**  
   端末紛失、機種変更、家族の端末、サポート対応。閉じるとロックアウトが増える。だからパスキーを足しても、パスワード欄を消さないサービスが多い。

2. **対応していないサービス・端末がまだ多い**  
   古いシステム、社内ツール、小さなサイト、組み込み機器。全部がWebAuthn対応ではない。利用者側も、毎日触るサービスの一部だけがパスキー対応、という状態になりやすい。

3. **端末やOSの壁がある**  
   Apple／Google／Microsoftなどでパスキーの置き場が分かれやすい。別のパソコン、別メーカーのスマホだと「あれ、出てこない」が起きる。困ると人が慣れているパスワードに戻る。

4. **見た目が任意のままだと、人は古い方を選ぶ**  
   「パスキーを設定」は出るが、すぐ横にいつものパスワードがある。説明も薄い。分からないものは飛ばされる。結果、入力回数の体感はパスワードのまま。

ここで一段落とす。

> だからパスワード入力が多いのは、パスキーが弱いからではない。弱い道がまだ開いたままだから、そこを通ってしまう。

接続：

- これが、二段階認証の話ともつながる。パスワードを残したまま足す方が、現場では楽。
- 本当に安全性を取り切るには、いつかパスワード経路を閉じる必要がある。そこが一番むずかしい。
- だから今の現実は「パスキーの時代の入口」であって、「パスワード消滅後」ではない。

やってはいけないこと：

- 「企業が怠慢」だけで片づける
- 「すぐ全部やめればよい」と簡単に言う（復旧設計がないと事故る）

### 6. 啓蒙より設計（約3分）

**目的：** 技術の話を、社会側の着地へ少しだけ広げる。説教にしない。

- 「良いパスワードを使おう」型の啓蒙は長く続いた。
- それでも被害は十分に減らなかった、という事実整理。
- 2025年、世界パスワードデーが世界パスキーデーへ移った、という象徴的な出来事。
- 言いたいこと：人を完璧にするより、失敗しても秘密が外へ出ない設計にする。

**注意：**
- 政治比喩・下ネタ比喩は使わない。
- 「バカでも安全」より「人が触れない／送らないようにしてある」と書く。

---

### 7. 締め（約2分）

**目的：** 行動を1つに絞る。

- 持ち帰り：パスワードとパスキーは名前が近いだけで、安全性の仕組みは別物。
- 補助の持ち帰り：よくあるスマホ指紋確認は二段階認証の追加であることが多い。パスキーはパスワード置換が本筋。
- 補助の持ち帰り2：今もパスワード入力が多いのは、パスキーが弱いからではなく、逃げ道と未対応が残っている移行期だから。
- 行動：証券・メール・主要なアカウントから、対応しているものへパスキーを追加する。
- 残す問い：「秘密を渡す設計」と「秘密を動かさない設計」。次に疑うべきはどちらの認証か。あと、自分のよく使うサービスはパスキー経路を本線にしているか、それとも任意のままか。
